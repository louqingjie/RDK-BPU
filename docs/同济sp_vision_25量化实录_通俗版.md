## 第 1 章：先补 6 个基础概念

### 1.1 模型 = 一张"计算流程图"

神经网络模型本质是一张**流程图**（术语叫计算图）：图片数据从左边流进去，经过几百个小格子加工，从右边流出来。每个格子做一种固定运算（叫**算子**），格子里的可调参数叫**权重**——训练就是调这些权重，部署就是原样执行它们。

### 1.2 量化 = 把小数压成整数

模型里流动的数本来是高精度小数（FP32，32 位存一个数）。**量化就是把这些小数按一个统一的"比例尺"缩放后，取整存成 8 位整数（INT8）**：

- 好处：文件小 4 倍、专用芯片算整数快得多（本例 BPU 上 36 ms → 仿真 4 ms 级别的差异）；
- 代价：取整必然有误差。比例尺定得越粗，误差越大。

整个量化的成败，就取决于**比例尺定得合不合理**。

### 1.3 精度 = 怎么衡量"误差有多大"

我们对比"量化前"和"量化后"的输出，用的是**余弦相似度**：两个答案向量方向有多一致，1 表示完全一样，0 表示完全无关。经验上 >0.999 算几乎无损。

⚠️ 但相似度高 ≠ 模型能用——第 5 章有一个相似度 0.997 却完全不能用的活例子。原因见 5.2 节。

### 1.4 BPU 与 CPU：两种完全不同的芯片

| | CPU（如 NUC 的 i7） | BPU（RDK X5 的专用芯片） |
|---|---|---|
| 工作方式 | 通用：拿到什么算什么 | **编译型**：模型先离线"编译"成芯片专用指令 |
| 能跑的算子 | 什么都能跑 | 只能跑编译器白名单里的算子 |
| 量化 | 可选（FP32 直接跑） | **必须**（只吃整数） |
| 本例速度 | 检测器 8.2 ms/帧 | 检测器 36.3 ms/帧（含后处理开销） |

所以部署到 X5 = 把模型交给**编译器**（hb_mapper），编译器负责把流程图翻译成 BPU 指令 + 顺便做量化。**编译通过只代表"翻译成功"，不代表"翻译得没走样"**——这是本次最重要的教训之一。

### 1.5 检测模型的三个段落

装甲板检测类网络通常分三段：

```text
输入图片 → [① 主干] → [② 检测头] → [③ 后处理] → 装甲板框+类别
           提取特征     判断"哪里有板、   阈值过滤、去重叠
           （看纹理形状） 是什么板、角点在哪" （一般不在图内，CPU 做）
```

本例两个模型的输出都是 **1×25200×22**：25200 个"候选位置"，每个 22 个数——**kpt 关键点坐标（0~640 的大数）、颜色类别分、数字类别分（小数）混在同一张表里**。记住这个结构，第 5 章的灾难就发生在这里。

### 1.6 格式与格式转换：充电器接口问题

同一个模型在不同框架里是不同文件格式：PyTorch 训练完导出 **ONNX**（通用格式），部署到 Intel CPU/GPU 的 OpenVINO 时再转成 **IR**（`.xml` + `.bin` 成对）。不同厂商的格式像不同品牌的充电器接口，**互不相通**。

- 地平线工具链只吃 **ONNX**；
- 同济只发布了 IR；
- IR → ONNX 没有官方反转换工具。

这个"格式死结"怎么解开的，见第 3 章。

### 2.1 同济方案的组成

|---|---|---|---|---|

| ~~主检测器~~ | 无网络 | 纯传统视觉：灰度化→二值化→找灯条轮廓→配对，代码里一行神经网络都没有 | — | — |

### 2.2 两个有意思的细节

1. **同济的"检测模型"配置里躺着一个 `use_traditional: true`**——网络检测器和传统检测器可以切换，但默认配置 `yolo_name: yolov5` 指向的还是 YOLO 网络。也就是说网络是他们的主力检测器。

## 第 3 章：发现一 —— 不用做格式转换，先找"原生同款"

### 3.1 死结

工具链要 ONNX，同济只给 IR。摆在前面的路看起来只有一条：把 IR 反向转回 ONNX。但 IR→ONNX **没有官方工具**；社区工具 `openvino2onnx` 又和容器里的 onnx 1.12 不兼容（它要更新版本的 onnx，而升级 onnx 会弄坏地平线工具链自己）。

### 3.2 转机：README 里藏着出处

同济 README 的参考文献里写着，他们的识别模型引自**深圳大学 RobotPilots 的 RM2024 识别模型开源**。顺着这条线找到了 [TOL0VE/RP24-DectionModel](https://github.com/TOL0VE/RP24-DectionModel)——里面有官方原始的 **`0708.onnx`**。

### 3.3 怎么证明"这就是同一个模型"？

不能光看名字像，我们做了**双引擎对齐验证**（`scripts/verify_sp25_models.py`）：

```text
同一份随机输入 ──┬──> 喂给 同济 yolov5.xml（OpenVINO 引擎跑）  ──> 输出 A
                └──> 喂给 深大 rp24_0708.onnx（ONNX 引擎跑）  ──> 输出 B
比较 A 和 B 的余弦相似度 = 1.0001   （阈值 >0.999，通过）
```

打个比方：怀疑两台"黑盒机器"内部是同一台，就给它们喂同一份原料，看产出的成品是否一样——结果两台机器的产出**一致到小数点后三位**，判定同一模型。

三项结构佐证也全部吻合：层名（`onnx::Conv_852` 这种 onnx 痕迹命名）、输入名（`images`）、通道剪枝数字（8/16/24/48/…/576 这类非常规通道数——这是被"剪枝瘦身"过的网络，不是官方原版 YOLOv5）。

**结论**：直接用深大官方 `0708.onnx`（全 FP32、opset 11，格式完全合规）走量化，保真度比任何反转换都高。这就是 P18 的"溯源优先于反推"。

⚠️ **边界说明**：1.0001 的整体相似度足以支持"同源模型"的判定（余弦理论上 ≤1，超出部分是浮点计算误差），但它是**随机输入、被坐标大数主导**的整体指标——不能证明逐通道一致。部署验收仍需真实图片的分通道对比与检出对照（见 5.5 节实验 ①）。

## 第 4 章：发现二 —— 分类器量化成功，"成功"长这样

### 4.1 两处小手术

tiny_resnet 本身条件很好（55 个节点全是 BPU 支持的算子、全 FP32 权重），但有两个人畜无害的小问题会挡住编译器：

| 问题 | 大白话 | 修法 |
|---|---|---|
| 输入 batch 是动态符号 | 图上写着"来几组图片都行"——编译器要求写死"一次就 1 组" | 把维度符号固化成 1（P20） |
| opset 17 | 这本"算子字典"是第 17 版，编译器只认到第 11 版 | 算子都没用新版才有的语义，直接把封面改贴"第 11 版"并通过校验（P19） |

### 4.2 生成校准集

量化要拿一批真实图片来"试表"（定比例尺）。分类器的真实输入是**从图里裁出来的 32×32 灰度装甲板小块**，我们用既有 640 校准图合成了 400 个样本（整图缩放 + 随机局部裁剪两种视角），预处理严格对齐同济 `classifier.cpp` 的写法（等比缩放贴左上角、黑底填充、/255）。

### 4.3 结果：教科书式的成功

| 指标 | 数字 |
|---|---|
| 编译 | ✅ 526 KB 的 `.bin`（原始 ONNX 1.1 MB，缩到约一半符合 INT8 预期） |
| 板端耗时 | **1.79 ms/帧** |
| 分类一致性 | 8 个测试样本 argmax 与高精度参考**全部一致**（证明量化未破坏分类能力；⚠️ 8 个随机裁剪样本 + 整图缩放视角不能代表真实装甲板数字输入，不等于分类准确率 100%） |
| 输出相似度 | logits 余弦 0.998 ~ 1.000 |

**量化成功长什么样**：文件变小、速度飞快、输出和量化前几乎一样、分类答案全对。四条全占。

## 第 5 章：发现三 —— 检测器"编译成功，识别全坏"

### 5.1 现象：三项全绿，一上板就露馅

检测器编译一路顺利（2.6 MB `.bin`，板端 36.3 ms，速度快得符合预期）。然后在固定阳性样本（一张确定有装甲板的图）上对比"电脑高精度参考"和"板端量化后"：

| 指标 | 大白话 | 电脑 FP32 | 板端 INT8 |
|---|---|---|---|
| 置信度峰值 | "最有把握的那个框有多确定" | **0.9804** | **0.6685** ↓ |
| 候选框数（>0.25） | "值得看的框有几个" | 57 个 | **1206 个** ↑↑ |
| Top10 框重合 | "两边最自信的 10 个框是同一批吗" | — | **0/10** |
| 颜色分相似度 | "红蓝灰认得对吗" | — | 0.59（基本报废） |
| 数字分相似度 | "数字认得对吗" | — | 0.76（严重走样） |

一句话：**模型变得"看什么都有装甲板"，但认颜色认数字全错**。这不是"差一点"，是完全不能用。

### 5.2 为什么相似度报告 0.997 也是假象

整体输出相似度显示 0.997——按 1.3 节的标准这不是挺好？**这是假象**：

打个比方：22 个输出通道像一张成绩单，其中 8 个格子填的是 0~640 的坐标大数，其余格子填的是 ±几的小分数。**算总相似度时，8 个大数把总分撑住了，14 个小分数全错了也看不出来**——就像班里两个学霸考满分把平均分拉到了 90，掩盖了其他 20 个人不及格。

所以**验收必须看"分通道成绩单"**（conf/color/num 各自单独对比），而不是看总分。这正是之前 rp_0526 踩过的同一个坑（踩坑记录 P14），本次原样复现。

### 5.3 抢救实验一：整体换 INT16，整体指标没救回来——但逐层数据推翻了旧解释

INT8 的比例尺太粗，自然的想法是：把误差大的地方换成 INT16（比例尺细 256 倍）。对照实验：

| 抢救方案 | conf 相似度 | 结果 |
|---|---|---|
| 默认 INT8 | 0.895 | 崩 |
| `int16_head` | 0.911 | **仍崩** |
| `all_int16` | 0.891 | **仍崩（整体指标反而更低）** |

**旧解释（已撤回）**："更精确反而更差 → 误差不在比例尺，在特征本身，检测头救不回"。

**2026-09-09 逐层复核推翻了它**。对比两个 quant_info 报告，INT16 把三个检测头 Conv 的数值精度大幅恢复了：

| 检测头 Conv | 默认 INT8 余弦 | `all_int16` 余弦 |
|---|---:|---:|
| `model.26/m.0/Conv` | 0.9134 | **0.9970** |
| `model.26/m.1/Conv` | 0.9630 | **0.9987** |
| `model.26/m.2/Conv` | 0.9767 | **0.9994** |

即：**特征量化误差这一层是可以用 INT16 修的**。整体 conf 相似度没改善、甚至"更差"，是因为整体指标被坐标大数主导（5.2 节的成绩单效应），**不能用它反推 INT16 无效**。rp_0526 上 0.83 的中间层低相似度属于局部现象，且被后续层拉回——"传话游戏、特征已传歪"的类比不成立。

### 5.4 结论修订：从"PTQ 无解"到"根因尚未闭环"

**原结论（已撤回）**："输出端手术、检测头 INT16、全网 INT16 三条路全部无效 → PTQ 无解，唯一出路 QAT"。

**撤回原因**：这三条路试的是"整体换精度"和"输出端手术"，而逐层证据显示 INT16 能把检测头精度恢复到 0.997+——PTQ 框架内至少还有未用尽的手段。三条路无效只能证明"这三种粗粒度做法无效"，**推不出"PTQ 无解"**。没有训练代码确实抬高了修复成本，但成本 ≠ 死路。

**修订后的结论**：

> **现有 PTQ 配置未达到可用精度，根因尚未闭环。**
> 已证实：默认 INT8 的检测头数值精度差，且可用 INT16 恢复（0.997+）。
> 未闭环的两个嫌疑：① **解码阶段的量化尺度**（当前重点嫌疑）；② 部署链路一致性。

**待区分的三类原因**：

1. **特征量化误差**——默认 INT8 检测头输出有明显偏差（校准范围、通道间动态范围差异、误差累积）。INT16 已证明可修，但当前证据不能进一步断言"剪枝导致"或"权重本身有问题"。
2. **解码阶段二次损坏（当前重点嫌疑，未证实）**——实际报告中，检测头之后部分张量的校准阈值达到**数千**（坐标解码后的量级），而 conf/cls logits 只有几个量级。若这些数共用较粗的量化尺度，小分数会被压坏——这能解释"head conv 精度恢复了、检出仍然全坏"。
3. **部署链路未排除**——输入布局、归一化、输出布局、反量化，任何一处不一致都会表现为"编译成功、结果全坏"。直接对比原始 ONNX 与板端输出，无法定位误差发生在哪一步。

保留的结论：

- **"模型能编译"和"量化后认得准"仍是两件独立的事**；
- 第三方模型"有没有训练工程"仍是重要的**成本**评估项（修复要绕的路更多），但不再是"能不能部署"的判决项；
- ONNX Runtime FP32 兜底（8.2 ms/帧 @NUC）仍是当前唯一确定可用的方案。

### 5.5 复核方法与下一步实验计划（2026-09-09）

**验收纪律（本节复核确立的规则）**：

1. 整体余弦相似度（0.997 / 0.891 / 1.0001）都被坐标大数主导，**不能作为"恢复/无救"的判断依据**；验收只认"真实图片 + 分通道误差 + 检出对照"。
2. **必须做阳性对照**：先用 host FP32 在确定含目标的图上跑出期望结果，再要求板端复现（P14/P16）。

**下一步实验（按优先级，替代"立刻重训"）**：

| 顺序 | 实验 | 能回答什么 |
|---|---|---|
| ① | 同一批真实图片，逐阶段对比：原始 ONNX → 转换后浮点模型 → 量化仿真 → 板端 | 误差出在模型转换、量化还是运行时？ |
| ② | 在三个检测头的**解码前**导出，分通道对比角点 / conf / 颜色 / 数字 | 提高精度后，真正有用的分数恢复了吗？ |
| ③ | 若解码前正常：把坐标解码与结果拼接移到 CPU（ONNX 图修改，**不需要训练代码**），并核对输出边界的量化尺度 | 能否绕开尾部混合值域造成的损伤？ |
| ④ | 若解码前已异常：定位首个显著失真的节点，针对性调整校准方法、范围或精度 | 哪个改动真正恢复检测？ |

**注意事项**：

- 截断位置要以**实际优化后的图**为准——解码乘法可能已被编译器融合进卷积；
- 不能只在最终输出处切片，此前丢掉的信息不会恢复；
- 校准集目前复用了另一模型的 200 张图片，需验证场景与预处理是否匹配，并按**检出率、误检率、分类准确率、角点误差**选择校准方案；
- X5 官方精度调优还有校准方法切换、偏置修正、敏感节点分析、尾部 CPU 回退等路径（[官方精度调优说明](https://developer.d-robotics.cc/oe_x5_doc/cn/oe_mapper/source/tune_content/accuracy_tune.html)），之后才考虑 QAT；
- 本节复核基于已有文件与报告，**未重新上板**，不承诺上述方案一定恢复精度。

## 第 6 章：给我们的三条启示

1. **编译成功 ≠ 能用。** "能不能编译"看的是算子类型清单，"量化后准不准"看的是权重数值分布。前者一分钟的 checker 就能过，后者必须上板拿阳性样本实测。
2. **相似度报告会骗人，要看分通道成绩单。** 大数值通道会掩盖小数值通道的崩坏；验收永远用"确定有目标的图"对比检出结果，而不是相信编译器打印的平均相似度。
3. **拿不到训练代码的第三方模型，修复成本更高，但不要轻易判死刑。** 抢救手段要按"逐层证据"排序：INT16 已证明能修特征量化误差（head Conv 0.997+），解码阶段尺度与部署链路是尚未排除的嫌疑；把"几次粗粒度抢救无效"直接推导成"只能重新训练"，证据不足。

| 对照 | 深大 rp_0526（2025 版） | 同济 sp25_yolov5（= 深大 RP24 0708，2024 版） |
|---|---|---|
| 编译 | ✅ | ✅ |
| 板端 BPU 耗时 | 4.95 ms | 36.3 ms |
| 精度 | conf 全零，0 检出 | conf 0.98→0.67，假阳性 ×21，分类通道报废 |
| INT16 抢救 | 整体指标未改善；**head Conv 逐层恢复 0.997+（5.5 节类推）** | 整体指标未改善；**head Conv 逐层 0.9134→0.9970 等（实测）** |
| 结论 | **根因未闭环**（重点嫌疑：解码阶段量化尺度、部署链路） | 同左 |

## 名词速查表

| 术语 | 一行解释 |
|---|---|
| 计算图 / 算子 / 权重 | 模型 = 流程图；格子 = 算子；格子里可调的参数 = 权重 |
| FP32 / INT8 / INT16 | 用 32 位 / 8 位 / 16 位存一个数；位数越少越快越小，但取整误差越大 |
| 量化（PTQ） | 把小数按比例尺压成整数；PTQ = 训练完成后直接压，不需重新训练 |
| QAT | 量化感知训练：训练时就"假装"自己在被量化，练出抗量化的权重 |
| 余弦相似度 | 两组输出的方向一致程度，1 = 完全一样 |
| 比例尺（scale） | 量化时"多大范围的小数映射到 0~255"的换算标准；被离群大数撑大后小数值全部失真 |
| 检测头（head） | 网络最后"下判断"的部分；本例为 model.26（rp_0526 为 model.24） |
| conf / logit | conf = "这是装甲板"的置信度；logit = 未过 Sigmoid 的原始分数，过 Sigmoid 后变 0~1 概率 |
| ONNX / OpenVINO IR | 两种互不相通的模型文件格式，像不同品牌充电器接口；工具链只吃 ONNX |
| opset | ONNX 算子字典的版本号，工具链最高认第 11 版 |
| batch | 一次同时喂几张图；量化编译要求写死（本例固化成 1） |
| 剪枝 | 训练后把不重要的通道删掉给网络"瘦身"，通道数会出现 8/24/48 这类非常规数字 |
| 阳性对照 | 用一张"确定有目标"的图先在电脑上跑出标准答案，再要求板端复现——验收的唯一可靠方式 |
