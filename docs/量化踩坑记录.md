## 阶段一：模型准备

### P1：模型内嵌后处理，BPU 无法编译

- **现象**：原始 ONNX 图内含 TopK / NMS / GatherND / NonZero（深大模型无此问题，AT_NN 模型有）。
- **原因**：导出时把后处理烧进了计算图；BPU 是编译型硬件，数据依赖算子无法编译。
- **解决**：深大模型后处理本来就在 CPU，无需处理；AT_NN 模型需裁剪（见可行性评估第 9 章）。

### P2：ONNX 以 FP16 导出，`makertbin` 报错

- **现象**：`makertbin` 在 `split_maxpool_into_multiples_pass` 阶段报 `unsupported input data type`，失败模型被存为 `*_pass_fail.onnx`。
- **原因**：PyTorch 导出时用了 FP16；图内所有张量（含 MaxPool 的输入输出）都是 FP16，工具链优化 pass 不支持。
- **解决**：**全图 FP16→FP32 转换**（`scripts/convert_model_fp32.py`）：120 个 FP16 权重、206 处类型声明全部转 FP32，并移除图首 Cast、改写内部 Cast。
- **教训**：只在图首加 Cast 转 FP32 输入**不够**——第一次尝试（`convert_input_fp32.py`，保留图内 FP16）在同一个 pass 失败。**必须整图 FP32**。
- **验证**：转换后先用 ONNX Runtime 跑一遍确认输出有限且形状正确，再送编译。

### P3：相机 SDK 头文件不完整 / 库符号链接断裂

- **现象**：编译采集程序报 `GXDef.h: No such file or directory`；`-lgxiapi` 链接失败。
- **原因**：板上 `~/program/sp_-vpie/third_party/.../include` 缺 GXDef.h；`/usr/lib/libgxiapi.so` 是指向不存在路径的断裂符号链接。
- **解决**：工作区 `Galaxy_camera_node/rm_camera_driver/include/daheng/` 的 GxIAPI.h 是自包含版本（不依赖 GXDef.h）；用实际存在的 armv8 库全路径链接：`~/program/carnival-the-age-solver/RM/rm_camera_driver/lib/armv8/libgxiapi.so`。

## 阶段二：量化编译

### P4：yaml 缺 `input_layout_rt`

- **现象**：`Parse 'input_parameters' failed! Input_layout_rt missing.`
- **原因**：`input_type_rt: 'rgb'` 时必须显式指定 `input_layout_rt`（nv12 不需要）。
- **解决**：补 `input_layout_rt: 'NCHW'`（或 NHWC，需与喂数据方式一致，见 P7）。

### P5：ONNX 图手术的四个语法坑

用 onnx 手工改图（输出归一化、拆分输出）时连环踩坑：

| 坑 | 现象 | 正确做法 |
|---|---|---|
| Slice 的 starts/ends/axes 类型 | `Type 'tensor(float)' of input parameter (sl_num_starts) is invalid` | 必须是 **int64** initializer |
| Clip 的 min/max（opset 11） | `Unrecognized attribute: max for operator Clip` | opset 11 起 min/max 是**输入**（标量 initializer），不是属性 |
| 标量 initializer | `min should be a scalar. NumDimensions() == 0 was false` | 形状必须是 `[]`（用 `numpy_helper.from_array(np.float32(v))`） |
| 图输出名与节点输出名不一致 | `Graph output (output_kpt) does not exist in the graph` | 图输出声明的名字必须与某个节点的输出名**完全一致** |

**教训**：每次改图后先 `onnx.checker.check_model` + ONNX Runtime 试跑 + 打印图输出名与节点输出名核对，再送编译。

## 阶段三：上板运行

### P6：`hrt_model_exec` 子命令名

- **现象**：`hrt_model_exec model_perf ...` 打印帮助而非执行。
- **解决**：子命令是 `perf` 和 `infer`（不是 `model_perf`）；多帧性能用 `perf --frame_count N`。

### P7：喂数据布局与 `input_layout_rt` 不一致 → 网格状垃圾检测

- **现象**：推理"成功"但输出全是网格状假框（conf 恰为 0.50、kpt 呈规则网格、每帧 ~1000 个候选），与 host FP32 行为完全不符。
- **原因**：模型按 `input_layout_rt: 'NHWC'` 编译，但测试脚本喂了 NCHW 排列的 uint8 数据——通道被拆散，模型看到的是乱码图像。
- **解决**：喂数据前确认排布与 `input_layout_rt` 一致。
- **教训**：**输出像垃圾时，第一步先怀疑输入喂错了**，而不是模型/量化坏了。判定方法：换一张确定有目标的图（阳性对照）+ 对比 host FP32 同图输出。

### P8：偶发 `hbDNNInitializeFromFiles failed, error code:-6000006`

- **现象**：同一模型、同一命令，有时加载失败（连续 30 次失败），过几分钟单次执行又成功；文件 md5 校验始终正确。
- **原因**：疑似连续快速加载/卸载时 BPU 资源释放竞争，或板端其他进程（CodeBuddy 远程服务占 118% CPU）导致的瞬时资源紧张。
- **解决**：板端脚本内**重试 3~5 次、每次 sleep 2~3 s**（`scripts/run_infer.sh`）；批量推理合并到单个 SSH 会话内串行执行。
- **附注**：降低占 CPU 进程的优先级（`sudo renice -n 19`）后 60 ms 级的 CPU 侧开销没有变化——那个是另一回事（见 P9）。

### P9：profiler 输出目录必须已存在

- **现象**：`--profile_path /tmp/prof_out` 报 `does not exsit!`（工具拼写还是原文）。
- **解决**：先 `mkdir -p`。

### P10：多帧逗号语法不是"批量帧"

- **现象**：`--input_file a.bin,b.bin,...` 报 `hbDNNGetInputTensorProperties failed -6000001`。
- **原因**：逗号分隔的 input_file 对应**多个模型输入节点**，不是多帧批量。单输入模型的多帧只能循环调用（或自己写 C 程序）。

## 阶段四：精度（本次最大的坑）

### P11：★ 输出混量纲被 per-tensor INT8 摧毁（conf 全零，0 检出）

- **现象**：编译、加载、BPU 推理全部正常（BPU 4.95 ms，与仿真一致）；无装甲板的暗图输出与 host FP32 一致（都是 0 检出，假阴性）；但**含装甲板的亮图**在板上 conf 全为 ~0.003（host FP32 为 0.978），0 检出。
- **逐通道诊断**：

  | 输出分支 | host vs 板端余弦相似度 | 状态 |
  |---|---|---|
  | kpt（归一化后） | 0.9984 | ✅ |
  | color | 0.7538 | ⚠️ |
  | num | 0.7742 | ⚠️ |
  | **conf** | **0.0073** | ❌ 全零 |

- **根因**：head 的 1×1 Conv 输出 66 通道（3 anchor × 22），**把 kpt 像素坐标（0~640）与 conf logit（±78）混在同一张量**。INT8 per-tensor 步长被 kpt 撑到 ~2.64，conf logit 误差 ±1.3~40，sigmoid 后置信度信息完全损毁。**量化损伤发生在 head Conv（BPU 内部），在任何输出端处理之前。**
- **已尝试且无效的方案**（全部失败于同一原因——手术位置在损伤点之后）：
  1. 输出张量归一化（kpt/640 + conf/color/num sigmoid）
  2. 拆成 4 个独立输出（各自量化 scale）
  3. conf 并入 kpt 输出（避免 [1,25200,1] 简并形状，见 P12）
  4. `calibration_type: 'mix'`（percentile 校准）
- **检测框坐标也是网格状**：kpt 通道步长同样被拉大（实测 ±17 px 误差），坐标呈 ~2.64×n 的格点分布。
- **正确修复路径**（2026-09-09 按 INT16 逐层证据重排，见阶段六复核）：
  0. **定位实验优先**：同批图片逐阶段对比（原始 ONNX → 浮点模型 → 量化仿真 → 板端）+ 检测头**解码前**分通道导出——先确认"解码阶段量化尺度"这一重点嫌疑
  1. **混合量化**：head Conv 层配 int16（步长降 64 倍；同架构 sp25_yolov5 已实测 head Conv 精度恢复 0.997+），需查 OE 混合量化 yaml 语法
  2. **分支级图手术**：在 3 个尺度的 head Conv（66ch）输出处切片为 kpt/conf/color/num 三组，kpt 组走原 decode 路径，其余过 Sigmoid 独立成张量。需先确认 head 后 Mul/Add 的逐通道常量语义（是否会对 sigmoid 后的值再乘 stride）
  3. **模型作者在导出脚本归一化输出**：kpt ÷640（或相对化）、conf/color/num 过 Sigmoid——让 head Conv 的所有输出在 0~1 量级。需导出代码或 best.pt
  4. 官方精度调优路径（校准方法切换/偏置修正/敏感节点分析/尾部 CPU 回退），之后才考虑 QAT

### P12：[1,25200,1] 简并形状输出被 runtime 清零

- **现象**：把 conf 单独作为图输出（形状 [1,25200,1]）时，板上该输出全为 ~0；同批的 [1,25200,8]、[1,25200,4]、[1,25200,9] 输出正常。
- **原因**：疑似 runtime 对最后一维为 1 的 3D 输出做 NHWC↔NCHW 布局转换时的实现缺陷。
- **解决**：把 conf 并入 kpt 输出（[1,25200,9]，值域同为 0~1），避开简并形状。
- **教训**：拆分输出时**避免最后一维为 1 的输出张量**。

### P13：runtime CPU 侧输出处理吃掉 ~25 ms

- **现象**：端到端 35~48 ms，而 `--profile_path` 显示 BPU 只有 4.95 ms。
- **定位**：

  ```text
  BPU_inference_time_cost:  4.95 ms
  Dequantize_output_HzDequantize:        32.7 ms   ← 55 万元素的反量化
  torch_jit_subgraph_0_output_layout_convert: 27.5 ms   ← NHWC→NCHW 大转置
  ```

- **判断**：55 万元素的简单反量化不该要 32 ms（板端 memcpy 吞吐实测 5.1 GB/s），是**逐元素跨步访问的实现问题**；且与模型无关（板端自带 DStereo 模型同样 ~46 ms）。
- **缓解**：C++ 部署时**申请 NHWC 输出**（推理前设置输出张量 layout 属性）可省布局转换 ~23 ms；反量化待与 runtime 版本/社区确认。
- **教训**：仿真只算 BPU；**大输出张量（≥1 MB）的 CPU 侧后处理要用 profiler 实测**。

### P17：后续逐点实测修正了 P11 的根因判断

> 2026-09-08，在固定阳性样本 `armor_test.bin` 上完成 FP32/板端逐点输出对比。

- **结论**：P11 中“66 通道检测头 Conv 的坐标值域直接撑大 INT8 量化步长”不是根因。检测头 Conv 的校准阈值仅约 17~24；坐标变到 0~640 是后续 `Mul/Add` decode 的结果。
- **逐点结果**：20×20 分支的 `model.10` 输入特征余弦相似度已降到 **0.833**；经过 `model.10` Conv / SiLU 后分别为 0.855 / 0.886。到检测头输入时为 0.810。损伤从深层主干特征开始累积，不是 head 单点量化。
- **已排除的 PTQ 修复**：输出拆分、head 局部 INT16、全局 Conv/Mul/Sigmoid INT16、`per_channel: True` 全部在同一阳性样本上 0 检出。全局 INT16 最大 conf 概率仅 0.012；per-channel 的 FP32 真目标 anchor logit 为 -16.17。
- **可用兜底**：板端安装 `onnxruntime` 后运行 FP32 ONNX 可恢复正确检测：最大 conf 0.9785、62 个候选，单帧约 **208 ms**。脚本为 `scripts/run_ort_fp32.py`；输入保持 NHWC uint8，脚本内部转换为 NCHW FP32/255。
- **长期修复**：该公开模型仓库只发布 ONNX，没有训练代码或 checkpoint；要获得 BPU 实时部署精度，需要模型作者提供 PyTorch 权重和训练/导出工程以进行 QAT，或改用已有 QAT 权重的模型。

## 阶段五：方法论教训

### P14：逐层余弦相似度会骗人，必须做阳性对照

- **现象**：量化报告显示输出层相似度 **0.9994**（全图平均 0.970），看似完美；实际 conf 通道全零、模型 0 检出。
- **原因**：相似度被 kpt 通道的大数值（±1 量级、占元素 8/22）主导，conf/color/num 通道的损毁被数学上掩盖。
- **对策**：**量化验收必须包含阳性对照**——用确定含目标的图像，验证"板上能检出、置信度合理、框/关键点位置正确"，而不是只看相似度报告。
- **配套工具**：`scripts/real_camera_test.py`（板端推理 + 后处理 + 标注图）。

### P15：仿真与实测的对应关系

| 指标 | 仿真 | 实测 | 结论 |
|---|---|---|---|
| BPU 推理延迟 | 4.2 ms | 4.95 ms | **准确**（社区经验"编译器乐观 2 倍"在本例未出现） |
| 端到端延迟 | — | 35~48 ms | 仿真不含 runtime CPU 侧开销，差距在此 |
| 检测结果 | — | conf 全零 | 仿真完全不反映量化精度问题 |

**结论**：仿真适合验证"能否编译、BPU 耗时量级"；**精度与端到端性能必须实机验证**。

### P16：负样本测试会漏报问题

- **现象**：暗图（无装甲板）上板端与 FP32 行为一致（都 0 检出）——**假阴性**，差点误判"量化成功"。
- **对策**：测试集必须包含**确定有目标且置信度已知**的阳性样本；先用 host FP32 跑出期望结果，再要求板端复现。

## 阶段六：同济 sp_vision_25 模型量化（2026-09-08）

> 对象：[TongjiSuperPower/sp_vision_25](https://github.com/TongjiSuperPower/sp_vision_25) 自瞄主链路实际在用的两个 NN 模型——`tiny_resnet.onnx` 数字分类器与 `yolov5.xml/bin` 装甲板检测器（OpenVINO IR，`yolo_name: yolov5` 实际生效）。主检测器为纯传统视觉，无可量化网络；打符模型不在自瞄链路，未纳入。

### P18：找不到原始 ONNX 时，先找"原始来源"而不是做格式反推

- **背景**：同济仓库只发布了 OpenVINO IR（torch_jit 转换，IR v11，权重 FP16），没有 ONNX。
- **弯路预警**：IR→ONNX 没有官方工具；社区 `openvino2onnx` 与工具链环境的 onnx 1.12 不兼容（依赖 onnx≥1.14 API，而升级 onnx 会破坏 hbdk）。
- **正解**：同济 README 引用的深大 RP24 识别模型开源（[TOL0VE/RP24-DectionModel](https://github.com/TOL0VE/RP24-DectionModel)）里有官方原始 `0708.onnx`。用 `scripts/verify_sp25_models.py` 双引擎对齐验证：同一随机输入跑 OV IR 与 ORT ONNX，输出余弦 **1.0001** → 判定同济 `yolov5.xml` ≡ `rp24_0708.onnx`，直接用原始 ONNX（全 FP32、opset 11）走量化，比任何格式反推都保真。
- **教训**：第三方 IR/工程转换模型，先溯源原始发布；同源数值验证（余弦 >0.999）通过即可绕开整个格式转换环节。
- **佐证**：layer 名 `onnx::Conv_852`、输入名 `images`、剪枝通道数（8/16/24/48/…/576）三项均与 0708.onnx 吻合。

### P19：opset 17 超出工具链上限（最高 11）

- **现象**：tiny_resnet（opset 17）checker 报 `The opset version of the model is 17, the maximum supported version is 11`。
- **坑**：`onnx.version_converter.convert_version(model, 11)` 在 onnx 1.12 下因 `No Adapter From Version $14 for Relu` 崩溃。
- **解决**：该模型算子（Conv/Relu/Add/MaxPool/GAP/Flatten/Gemm）在 opset 11 全部合法且无版本敏感语义 → 直接改写 `opset_import` 声明为 11，`onnx.checker` 验证 + checker 复检通过（`scripts/prepare_sp25_models.py` 内置该兜底逻辑）。
- **边界**：声明改写只对"算子语义跨版本未变"的模型安全；含 Resize/Pad/Scan 等版本敏感算子时必须走真正的版本转换或重导出。

### P20：动态 batch 输入必须先固化

- **现象**：tiny_resnet 输入为 `['batch_size',1,32,32]` 动态符号，量化编译要求静态 shape。
- **解决**：固化 batch=1 后量化（同脚本一并处理）。

### 量化结果

| 模型 | 编译 | 板端 BPU | 精度验收（armor_test / 校准样本对照） | 结论 |
|---|---|---|---|---|
| sp25_tiny_resnet（1.1MB 分类器，526KB bin） | ✅ | **1.79 ms** | 8/8 样本 argmax 一致，logits 余弦 0.998~1.000 | ✅ **量化成功** |
| sp25_yolov5（2.6MB bin，剪枝 YOLOv5+MobileNetV3） | ✅ | 36.3 ms | 整体 cos 0.997 但 conf 崩坏：max_prob 0.980→0.669，假阳性 57→1206，top10 anchor 重合 0/10，color cos 0.59 / num cos 0.76 | ❌ **现有配置不可用，根因未闭环** |

- yolov5 精度症状与 rp_0526 的 P11 完全同款（分类通道毁坏、kpt 格点化，整体相似度被 kpt 大值掩盖——P14 再验证）。
